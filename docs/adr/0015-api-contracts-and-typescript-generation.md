# ADR-0015: API Contracts and TypeScript Type Generation

**Date**: 2026-07-24  
**Status**: Accepted  
**Deciders**: Meal Forge Frontend + Backend Teams

## Context

Meal Forge has four independent microservices (Identity, Catalog, Planning, Shopping) that expose HTTP REST APIs consumed by the Next.js frontend. As the project evolves:

- Frontend and backend are developed in parallel by potentially different developers/agents
- API contracts can drift (backend returns `productId`, frontend expects `product_id`)
- Breaking changes are discovered late (at integration time, not at type-check time)
- Manual type definitions in the frontend are error-prone and require manual synchronization

## Decision

**Establish API contracts via OpenAPI 3.0 specs** (auto-generated by FastAPI) and **generate TypeScript types** from those specs using `openapi-typescript`. This ensures:

1. **Single source of truth**: FastAPI's OpenAPI spec is canonical
2. **Type safety**: Frontend TypeScript client code is checked against actual API responses at build time
3. **Breaking change detection**: Type mismatches surface before deploy
4. **Zero manual sync**: Types are generated from the spec, never hand-written or duplicated

## Implementation

### Phase 1: FastAPI OpenAPI Configuration

Each service's `main.py` already uses `FastAPI(title="...", version="...")` which auto-generates OpenAPI at `/openapi.json`.

**Enhance with metadata** (add to each service):
```python
app = FastAPI(
    title="Identity Service",
    version="0.1.0",
    description="Account lifecycle and session management",
    servers=[
        {"url": "http://localhost:8001", "description": "Local development"},
        {"url": "https://api.mealforge.com", "description": "Production"},
    ],
)
```

**Result**: OpenAPI spec available at:
- `http://localhost:8001/openapi.json` (identity)
- `http://localhost:8002/openapi.json` (catalog)
- `http://localhost:8003/openapi.json` (planning)
- `http://localhost:8004/openapi.json` (shopping)

### Phase 2: TypeScript Type Generation

**Frontend setup** (`frontend/`):

1. Add `openapi-typescript` to devDependencies:
   ```bash
   npm install --save-dev openapi-typescript
   ```

2. Add generate script to `package.json`:
   ```json
   "scripts": {
     "generate:api": "openapi-typescript http://localhost:8001/openapi.json -o src/lib/api/types/identity.ts && openapi-typescript http://localhost:8002/openapi.json -o src/lib/api/types/catalog.ts && openapi-typescript http://localhost:8003/openapi.json -o src/lib/api/types/planning.ts && openapi-typescript http://localhost:8004/openapi.json -o src/lib/api/types/shopping.ts"
   }
   ```

3. Create wrapper at `src/lib/api/clients/` that exports typed fetch functions:
   ```typescript
   // src/lib/api/clients/identity.ts
   import type { paths as IdentityPaths } from '../types/identity'
   import { createFetch } from './shared'

   const fetch = createFetch(
     process.env.NEXT_PUBLIC_IDENTITY_URL || 'http://localhost:8001'
   )

   export async function getSession(
     token: string
   ): Promise<IdentityPaths['/auth/session']['get']['responses'][200]['content']['application/json']> {
     return fetch('/auth/session', {
       headers: { Authorization: `Bearer ${token}` }
     })
   }
   ```

**Generated type structure** (example from identity.ts):
```typescript
export interface paths {
  '/auth/register': {
    post: {
      requestBody: {
        content: {
          'application/json': {
            email: string
            password: string
          }
        }
      }
      responses: {
        201: {
          content: {
            'application/json': {
              account_id: number
              email: string
              role: 'user' | 'nutritionist'
            }
          }
        }
        409: { description: 'Email already registered' }
      }
    }
  }
  // ... more endpoints
}
```

### Phase 3: API Contract Documentation

Create `docs/api-contracts.md` documenting:

1. **Service endpoints by module** (CARD-XXX alignment)
   - Which endpoints belong to which feature
   - Auth requirements (Bearer token, no auth, etc.)

2. **Data models & enums** (shared across endpoints)
   - `AccountRole` enum: user | nutritionist
   - `MealSlot` enum: breakfast | lunch | dinner | snacks
   - `Product`, `Assignment`, `ShoppingList` shapes

3. **Error handling & fallbacks**
   - Which services are optional (Shopping can survive no Catalog)
   - Which status codes need special handling (401 → redirect to sign-in, 503 → stale banner)

4. **Request/response examples** for critical flows
   - Sign-in (with token capture)
   - Create meal assignment (with nutrition denormalization)
   - Generate shopping list (with concurrent cross-service calls)

## Benefits

| Aspect | Before | After |
|--------|--------|-------|
| Type errors | Caught at runtime (e.g., property access on undefined) | Caught at build time (TypeScript strict mode) |
| API changes | Manual review of PR diffs + guessing if frontend breaks | Types won't compile if API contract breaks |
| Sync effort | Manual: update Pydantic schema + manually update TS types | Automatic: run `npm run generate:api` after backend change |
| Onboarding | Read scattered Swagger docs + guess at shapes | Read generated types in IDE, use Ctrl+click to see definition |
| Fallback behavior | Implicit; frontend doesn't know service is unavailable | Explicit: document in API contract docs which calls can fail |

## OpenAPI Best Practices

To get the most from this setup:

1. **Keep Pydantic schemas in sync with FastAPI routes** — OpenAPI is generated from route type hints and Pydantic models
   ```python
   from pydantic import BaseModel
   
   class AccountResponse(BaseModel):
       """Account detail (no password)"""
       account_id: int
       email: str
       role: RoleEnum
   
   @app.get('/account', response_model=AccountResponse)
   async def get_account(token: str = Depends(verify_token)):
       ...
   ```

2. **Use response models, not inline dicts** — OpenAPI reflects response models exactly
   ```python
   # Good: OpenAPI will include AccountResponse schema
   @app.post('/auth/register', response_model=AccountResponse, status_code=201)
   async def register(...):
       ...
   
   # Bad: OpenAPI schema is inferred and may be incomplete
   @app.post('/auth/register')
   async def register(...):
       return {'account_id': 1, ...}  # loose typing
   ```

3. **Document error responses** — FastAPI's `responses` parameter
   ```python
   @app.post(
     '/auth/register',
     response_model=AccountResponse,
     responses={
       409: {'description': 'Email already registered'},
       422: {'description': 'Invalid request body'},
     }
   )
   async def register(...):
       ...
   ```

4. **Add field descriptions** — shown in OpenAPI and IDE hints
   ```python
   class Product(BaseModel):
       id: int = Field(..., description='Product ID')
       name: str = Field(..., description='Product name (localized or English fallback)')
       calories_per_100g: float = Field(..., ge=0, description='Calories per 100g')
   ```

## Testing the Contract

**Manual**:
```bash
# Terminal 1: start all services
docker compose up

# Terminal 2: generate types
cd frontend && npm run generate:api

# Check generated types
cat src/lib/api/types/identity.ts  # TypeScript types from Identity service spec

# Build and typecheck
npm run build
```

**Automated** (CI/CD):
```bash
# In GitHub Actions / CI pipeline
npm run generate:api && npm run build
# Fails if backend spec breaks frontend types
```

## Maintenance

| Scenario | Action |
|----------|--------|
| Backend adds new field to response | Run `npm run generate:api`, TypeScript will error if frontend expects old shape, fix at compile time |
| Backend renames endpoint | FastAPI route changes, `npm run generate:api` removes old path from types, Frontend IDE shows "property not found" |
| Frontend uses a new backend endpoint | Check generated types for request/response shapes; IDE autocomplete guides you |
| Third-party integrator needs API | Share the OpenAPI spec or generated TypeScript types; no manual documentation needed |
